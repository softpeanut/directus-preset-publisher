Publishing Deterministic Configuration from Directus

Let editors change marketplace image presets without letting malformed CMS data silently alter a browser image pipeline.

A reproducible implementation note · Node.js 22 · Directus 12.3.1 · SDK 25.0.1

Hard-coded configuration has an attractive property: it changes only when code changes. It also has an operational cost. An editor who needs to disable a preset or correct a label must ask for a code release. Moving the rows into a content management system removes that bottleneck, but it also replaces compiler-reviewed input with runtime data. A blank label, an accidental stretch mode, or two active rows with the same key can now reach the product unless the publishing boundary rejects them.

I built a small Directus example to test a narrower contract: editors may manage non-sensitive image-export metadata, while a build step remains responsible for turning that metadata into a deterministic JSON artifact. Product images never enter Directus. The complete implementation and tests are in the Directus Preset Publisher repository.

The boundary is the product

The collection contains seven fields: marketplace slug, display label, width, height, fit mode, background color, and an active flag. Directus supplies a useful editing surface and authenticated API. It does not decide whether a row is safe to publish. That decision belongs to a small pure function outside the CMS.

The function normalizes strings, converts dimensions to numbers, and then enforces a deliberately small schema. Marketplace identifiers must be lowercase slugs. Dimensions must be integers from 1 through 10,000. Mode is either contain or cover. Background is a six-digit hexadecimal color. A label cannot be empty.

const MODES = new Set(['contain', 'cover']);
const HEX_COLOR = /^#[0-9a-f]{6}$/i;
const SLUG = /^[a-z0-9]+(?:-[a-z0-9]+)*$/;

if (!SLUG.test(preset.marketplace)) {
  throw new Error('marketplace must be a lowercase slug');
}
if (!Number.isInteger(preset.width) || preset.width < 1 || preset.width > 10000) {
  throw new Error(`width is invalid for ${preset.marketplace}`);
}

This is stricter than relying on field controls in the admin interface. Interface controls improve editing, but data can also arrive through imports, migrations, or API clients. The export boundary must validate the values it actually receives.

Determinism requires removing plausible metadata

After validation, the publisher filters inactive rows and sorts the remainder by marketplace slug. It rejects duplicate active slugs and rejects an empty active set. The document contains only the presets array:

{
  "presets": [
    {
      "marketplace": "amazon",
      "label": "Amazon main",
      "width": 1600,
      "height": 1600,
      "mode": "contain",
      "background": "#ffffff",
      "active": true
    }
  ]
}

There is intentionally no generated timestamp. A timestamp looks informative, but it makes two exports of unchanged source data differ byte for byte. Source control already records when an artifact was committed, and a deployment system can record when it was published. Putting the wall clock inside the content would make meaningful review harder without improving the preset contract.

The writer uses Node's exclusive-create flag, wx. If the destination already exists, the command stops rather than overwriting a previously reviewed artifact. The operator must make that replacement explicit.

The important result is not “the CMS exported JSON.” It is that the same accepted inputs produce the same ordered bytes, while malformed or ambiguous inputs stop publication.

Keep privileged access at build time

The browser image tool does not query Directus. An authenticated Node process reads only the seven named fields and writes the static artifact. That has three useful consequences:

  • Directus credentials do not ship to the browser.
  • Product photos remain in the user's browser and never become CMS records.
  • The runtime consumes a small reviewed file instead of inheriting CMS availability and permission complexity.

The example uses an admin client because it also includes a local schema seed. A production system should use a least-privilege build identity for the read step and keep administrative credentials limited to schema operations. The repository does not claim to be a hosted production configuration.

Test the rejected states

The four Node test cases are compact because the validation core has no network dependency. They cover normalization, invalid dimensions, an unsupported mode, a non-hex color, a path-like slug, deterministic ordering, duplicate active slugs, and an empty export. One test sends the presets in shopify-then-amazon order and asserts that the result is amazon-then-shopify.

That test does not prove Directus itself is reliable, nor does it prove that a marketplace currently accepts a given image size. It proves the narrower property owned by this module: accepted rows are normalized and ordered consistently, and specified invalid states fail before a file is published.

Reproduce the result

The repository pins Node.js 22 because the tested native dependency chain did not install on Node.js 26. With Node 22 active:

git clone https://github.com/softpeanut/directus-preset-publisher.git
cd directus-preset-publisher
npm install
cp .env.example .env
# Replace the local-only SECRET and ADMIN_PASSWORD values.
npm run directus:bootstrap
npm run directus:start

In a second shell with Node 22 active, the package scripts load the same .env file explicitly:

npm run seed
npm run export -- /tmp/presets-a.json
npm test

# Remove or choose a second path because export will not overwrite.
npm run export -- /tmp/presets-b.json
cmp /tmp/presets-a.json /tmp/presets-b.json

cmp exits successfully only if the two exports are byte-identical. To inspect the failure path, change one active row to an unsupported mode or duplicate a marketplace slug, choose a fresh output path, and rerun the export. It should exit without producing an accepted artifact.

What this pattern does not solve

This example does not certify marketplace rules, deploy Directus, define a production permission model, or provide an approval workflow. It also does not validate arbitrary image transformations. Those are separate responsibilities. The pattern is useful precisely because it keeps its claim small: editable configuration can cross from a CMS into a static product only through a deterministic, fail-closed publishing boundary.

That boundary makes CMS convenience compatible with code-reviewable output. Editors gain control over safe metadata. The application keeps credentials and files out of the client. Reviewers see stable diffs. And an invalid row becomes a failed build rather than a quiet production surprise.
